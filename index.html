    How it reads a log

    Parsers turn each format into one event shape, so rules never depend on log layout. Rules are YAML data, validated before a single line is read, and each runs as a sliding window over time.

    match
    One line carries the attack. SQL injection, path traversal and cross-site scripting in a URL, a scanner's user agent.
    threshold
    One address repeats inside a window. Ten failed SSH logins in five minutes.
    distinct
    One address touches many values. Ten different accounts tried from one address is password spraying; thirty different missing paths is directory scanning.
    sequence
    One event follows many others. A successful login after five failures from the same address.

    Log content is treated as hostile. A crafted username cannot spoof the source address, layered URL encoding is undone before matching, out-of-order lines are put back in time order, and evidence is escaped wherever it is shown.

    Labelled synthetic logs

    All 13 labelled attacks found. One false positive, kept on purpose: a harmless search for “union select” looks exactly like SQL injection in a log line.

    Speed

    One million web log lines in about 64 seconds on a laptop with the command-line tool, around 15,600 lines per second. In this page the same code runs in WebAssembly and is slower.

    What it does not do

    • It detects; it does not block. It is not a firewall or a hosted service.
    • Web logs hold no request bodies, so attacks sent in a POST are invisible.
    • Attacks slowed below a threshold, or spread across many addresses and accounts, do not fire.
    • Anyone who can write whole log lines can forge events. Logs must be protected where they are written.
    • Signatures miss what they were not written for: about a third of the independent injection and traversal strings get through.
